# Teams API migration roadmap

Updated 2026-10-08 against repository version 0.10.0. This compares the retained web-based adapter with the current API adapter; it describes repository support, not deployment status on the central Switchboard.

The comparison uses the [web operation contracts](lib/openapi.js), [web router](legacy-index.js), [browser implementation](lib/browser.js), [API operation contracts](lib/api-openapi.js), [API router](index.js), [API implementation](lib/teams-api.js), and [triage implementation and gates](lib/triage.js). Keeping an operation ID does not necessarily preserve its earlier behavior.

## Gaps compared with the web-based version

| Capability / previous call | Web-based behavior | Current API behavior | Remaining work |
| --- | --- | --- | --- |
| Message search: `searchTeamsMessages` | Native server-backed search across chats/channels, with bounded result pagination. | `/search/messages` is absent from OpenAPI and returns unsupported. | Implement verified API search, result pagination and explicit coverage. Searching downloaded recent messages would not restore server-search parity. |
| Open search result: `openTeamsSearchResult` | Reopens an exact result and returns chat/message IDs or channel/root context. | `/search/messages/open` is absent; old search handles cannot be resolved. | Resolve exact API search hits into usable chat or channel-thread context, with account binding and stale-result handling. |
| People search: `searchTeamsPeople` | Searches the native people picker by name or email. | The same operation ID accepts only an exact email/UPN and returns one exact match. | Restore name-based discovery and multiple candidates while preserving exact identity checks before a write. |
| New one-to-one chats: `startTeamsConversation` | Opens an existing or new conversation for an exact directory person; an initial send can persist a new chat. | The same operation ID only resolves one existing one-to-one chat in the conversation snapshot. It cannot create a chat for a new recipient. | Verify chat creation and initial-send contracts, membership, duplicate prevention and restart recovery. |
| Person mentions in structured content | Exact-email mention runs work in rich chat/channel sends and structured edits through native autocomplete. | The API schema removes mention runs; `messagePayload` refuses them. Editing a message that already contains mentions is also refused. | Implement verified person mention metadata/rendering and identity resolution for sends, replies and edits. Preserve refusal of stale or ambiguous identities. |
| Channel parent listing: `listTeamsChannelThreads` | Lists rendered parent messages in a Threads channel, including read threads. | The legacy route is absent. Triage can discover bounded unread channel roots, but is not a general parent-listing replacement. | Add explicit channel-root listing with continuation and coverage; do not depend on an unread triage target. |
| Exact channel-thread read: `readTeamsChannelThread` | Opens an exact channel/root pair and reads its replies. | The legacy route is absent. Triage reads bounded thread context only for discovered targets. | Add an exact channel/root read that works for read as well as unread threads and can locate older roots. |
| Channel-thread history/export: `pageTeamsChannelThreadHistory` | Resumable history and NDJSON export for one exact root and its replies. | Chat history and channel-level history exist; the per-thread history route is absent. Channel-level history reads the base channel conversation and does not replace traversing each root's replies. | Add per-root backward-link pagination, deduplication, cursor replay and NDJSON export. |
| Start a channel thread: `startTeamsChannelThread` | Native Threads-layout top-level sends, with plain or structured rich content. | The legacy route is absent; no enabled API capability starts a channel thread. | Capture and verify top-level channel send contracts separately from replies, then add durable sends and permission checks. |
| Reply to a channel thread: `replyTeamsChannelThread` | Native reply to an exact channel/root pair. | The legacy route is absent. A triage reply candidate exists, but `channelReplies=false`; it cannot send in production. | Verify the request and that the reply appears beneath its intended root before enabling the gate; restore the direct route or document a complete replacement. |
| Quote an arbitrary chat message: `sendTeamsMessage` with `replyToMessageId` | Native quoted replies to an exact message from ordinary chat reads, within bounded history lookup. | The original parameter is rejected. `replyTeamsBatch` supports native quotes through ephemeral triage targets from bounded inbox/context reads; it is not a general exact-ID quoting replacement. | Restore a verified exact conversation/message reply locator or compatible parameter, including older and already-read messages. Chat quotes have source/fixture evidence but still need a designated-chat live send. |
| Mark a chat unread: `markTeamsChatUnread` | Chat-level action needing only chat ID and idempotency key. | The legacy `/chats/{chatId}/unread` route is absent. `setTeamsReadState` supports live-verified selected-message chat unread, but requires a message boundary or triage target. | Decide whether to restore the old chat-level contract or provide an explicit migration path for callers that have only a chat ID. Do not silently invent a selected cutoff. |
| Notes/self-chat access | The web adapter can open the native Notes conversation when exposed; its read-state requests were captured during verification. | `48:notes` is absent from standard CSA listing and cannot pass the API resolver's listed-membership check. | Verify account-bound discovery/resolution for special self-chat IDs. Do not bypass membership checks for arbitrary thread IDs. |
| Discovery beyond a partial snapshot | Unread/chat/channel discovery can traverse virtualized sidebar sections up to its scan bound. Neither adapter guarantees a complete account archive. | Listing uses one CSA snapshot, which can be partial. Triage cursors continue over sources/roots already discovered; they do not fetch chats omitted from that snapshot. | Implement verified conversation-service continuation or another discovery path, with explicit completeness and large-account tests. |
| Mutation confirmation | Web writes verify an observed message, edit, tombstone or selected reaction state in the UI. This was not a delivery receipt. | Sends, edits, deletion and reactions usually report `accepted_by_api` without post-write message-state verification. Explicit read-state updates do perform readback. | Add bounded read-after-write confirmation where the API permits it, while preserving accepted results, durable uncertainty and the distinction from recipient delivery. |

The eight legacy operation IDs absent from the current API schema are `searchTeamsMessages`, `openTeamsSearchResult`, `listTeamsChannelThreads`, `startTeamsChannelThread`, `readTeamsChannelThread`, `replyTeamsChannelThread`, `pageTeamsChannelThreadHistory`, and `markTeamsChatUnread`. The table also records regressions hidden behind retained IDs and features available through narrower replacement calls.

## Supported functionality with remaining consistency work

- **Chat read/unread:** `setTeamsReadState` is enabled and live-verified. It preserves the ordinary horizon and uses a separate explicit unread bookmark. Durable unread generations supersede older automatic read grants across restart. The flat `listUnreadTeamsMessages` implementation still treats a zero `userConsumptionHorizon` as an unknown boundary, whereas triage correctly treats it as a cleared bookmark and falls back to the ordinary horizon. Align these helpers and verify mixed read-state/unread-list workflows.
- **Reactions:** listing and desired-state mutations are implemented. The API's advertised `available` list is fixed to six reaction IDs, whereas the web adapter discovered the target's quick reactions and existing visible pills. The API also returns reaction keys found on the message and accepts validated reaction IDs, so this is an availability/discovery and live-contract verification gap, not proof that every other reaction is rejected. Restore trustworthy availability reporting and verify existing/custom reaction behavior.
- **History:** chat and channel-level pagination, cursor replay and NDJSON are implemented. Legacy `maxWindows`, UI anchor fields and response shapes have changed; cursors are not portable between adapters. Document replacement parameters and verify deep pagination/retention behavior. Per-thread channel history remains a separate missing capability above.
- **Connection and ID migration:** old DOM-only connections need reconnecting. Legacy IDs containing an exact thread ID can migrate after membership lookup; sidebar-only, recipient/search handles and old cursors cannot. Retain explicit migration errors and refresh IDs through current listing/resolution calls.
- **Capability reporting:** expose both missing operations and narrowed input/coverage contracts. In particular, quoted replies and chat unread now have API replacements, while their legacy entry points remain unsupported. Channel thread reads are bounded triage support, not full channel-thread route/history parity.

## Disabled capabilities and proposed extensions

These remain distinct from missing web parity:

| Work | Status / enabling condition |
| --- | --- |
| Explicit channel read/unread | Both gates are false. Verify native marker scope in a designated channel and prove that unrelated unread sibling threads remain protected. The web plugin had read side effects when opening channels, not a dedicated selected-message channel read-state contract. |
| Automatic read-after-reply | `readAfterReply=false`. The durable read stage is fixture-tested, but needs independent verification of bookmark handling and unread-generation protection before enabling it. This is a new explicit workflow, not a removed standalone web operation. |
| Channel replies | This **is** missing web parity. Keep the candidate disabled until exact-root native request and live-send verification passes. |

Attachments/file upload, group-chat creation, arbitrary full emoji-picker search, and legacy Posts-layout channel writes were not supported by the retained web plugin. They may be future extensions, but should not be counted as API-migration regressions. Both adapters bound reads and exclude unavailable/retained/deleted history; neither guarantees a full account archive.

## Remaining validation from earlier roadmap entries

- **Live message writes:** validate plain/formatted chat sends, quoted replies, edits, deletion and reactions in designated conversations. No live message was sent during the read-state work. Fixture success and enabled source-verified chat quotes are not evidence of a live send.
- **Channels:** validate actual root/reply coverage and deep per-thread traversal before claiming full thread parity; native channel sends and marker scope have not been designated or live-verified.
- **Central Switchboard:** validate imported-token connections, server HTTP renewal, laptop `auth:sync`, reconnect/account binding and durable ledger recovery on the central host. Local Mac validation does not establish central-host behavior.
- **Authentication expiry and recovery:** test rotation across the SPA refresh-token expiry boundary, terminal revocation/MFA recovery and tenant-specific sign-in policy. HTTP renewal has passed locally; token lifetime and headless cookie-only reacquisition remain unverified.
- **Diagnostic session reuse:** the shared owner-only cache and refresh-rotation persistence have restart/account/concurrency fixture coverage. Its first live shared-cache run and reuse across subsequent commands remain to be validated. Reuse a saved session for live checks; request fresh browser capture only when testing capture or when renewal cannot recover it.
- **Scale and concurrency:** validate partial discovery, large-account pagination, older roots/replies and external changes during writes. Existing-message suffix preservation passed live; newly injected arrivals and races have fixture coverage. Private endpoints offer no atomic compare-and-set.
- **Independent review:** review private API contracts, uncertainty handling and migration compatibility before relying on broader write support.

## Completed evidence and changes

- **0.10.0:** selected-message chat read/unread batches, native horizon/bookmark captures and browser-closed regular-chat readback passed on 2026-10-08. Checks covered inclusive boundaries, preserving an existing later unread message, replay without restoring old unread intent, and restoration to the test chat's original read state. The ordinary horizon was never rewound. Channel gates and automatic read-after-reply remain disabled. Shared diagnostic session persistence and HTTP refresh reuse are implemented. The full suite passed 137 tests. See [protocol evidence and limits](docs/triage-protocol.md).
- **0.9.0:** grouped paginated triage, batched context refresh and source-verified native quoted chat replies are implemented. Browser-closed inbox/context reads passed locally; channel completeness and live quoted sends remain separate validation work.
- **0.8.1:** laptop `auth:sync` implements readiness/expiry checks, a server renewal probe, in-memory token reconnect upload and status verification; central-host live validation remains outstanding.
- **0.8.0:** browser refresh-token capture, browser-closed HTTP renewal of both Microsoft access tokens, chat-token exchange/account binding, profile and conversation reads passed locally. Production on-demand renewal, rotated-token storage and portable version 2 bundles have fixture coverage. Imported connections do not launch a browser on the host.

Earlier statements that chat read markers were entirely unverified or that the Node adapter still needed its first local read-only check are superseded by this evidence. Completed local checks do not close the central-host, broader-write or expiry-policy items above.
