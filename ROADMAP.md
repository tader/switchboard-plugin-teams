# Teams API migration roadmap

Updated 2026-10-08 against repository version 0.11.0. This compares the retained web-based adapter with the current API adapter; it describes repository support, not deployment status on the central Switchboard.

The comparison uses the [web operation contracts](lib/openapi.js), [web router](legacy-index.js), [browser implementation](lib/browser.js), [API operation contracts](lib/api-openapi.js), [API router](index.js), [API implementation](lib/teams-api.js), and [triage implementation and gates](lib/triage.js). Keeping an operation ID does not necessarily preserve its earlier behavior.

| --- | --- | --- | --- |
| Message search: `searchTeamsMessages` | Native server-backed search across chats/channels, with bounded result pagination. | Restored with server-backed Substrate queries, bounded pagination and deduplication. Live queries passed. | Validate large searches and tenant coverage; queries require renewal credentials for an optional search token. No local recent-message scan substitutes for search. |

| People search: `searchTeamsPeople` | Searches the native people picker by name or email. | Restored name search with up to 20 server directory suggestions; exact email remains a verified profile lookup. | Reply to a channel thread: `replyTeamsChannelThread` | Native reply to an exact channel/root pair. | The legacy route is absent. Do not silently invent a selected cutoff. |
| Notes/self-chat access | The web adapter can open the native Notes conversation when exposed; its read-state requests were captured during verification. | `48:notes` is absent from standard CSA listing and cannot pass the API resolver's listed-membership check. | Verify account-bound discovery/resolution for special self-chat IDs. Do not bypass membership checks for arbitrary thread IDs. |

The three legacy operation IDs still absent from the current API schema are `startTeamsChannelThread`, `replyTeamsChannelThread`, and `markTeamsChatUnread`. The table also records regressions hidden behind retained IDs and features available through narrower replacement calls.

## Supported functionality with remaining consistency work

- **Chat read/unread:** `setTeamsReadState` is enabled and live-verified. It preserves the ordinary horizon and uses a separate explicit unread bookmark. Durable unread generations supersede older automatic read grants across restart. The flat `listUnreadTeamsMessages` helper and triage now share effective-boundary logic: a zero bookmark falls back to the ordinary horizon; a positive bookmark takes precedence. Regression checks cover cleared, active and unknown boundaries and own-message exclusion.
- **Reactions:** listing and desired-state mutations are implemented. The API's advertised `available` list is fixed to six reaction IDs, whereas the web adapter discovered the target's quick reactions and existing visible pills. The API also returns reaction keys found on the message and accepts validated reaction IDs, so this is an availability/discovery and live-contract verification gap, not proof that every other reaction is rejected. Restore trustworthy availability reporting and verify existing/custom reaction behavior.
- **History:** chat and channel-level pagination, cursor replay and NDJSON are implemented. Legacy `maxWindows`, UI anchor fields and response shapes have changed; cursors are not portable between adapters. Document replacement parameters and verify deep pagination/retention behavior. Per-thread history is restored; deep live reply traversal remains validation work.
- **Connection and ID migration:** old DOM-only connections need reconnecting. Legacy IDs containing an exact thread ID can migrate after membership lookup; sidebar-only, recipient/search handles and old cursors cannot. Retain explicit migration errors and refresh IDs through current listing/resolution calls.
- **Capability reporting:** expose both missing operations and narrowed input/coverage contracts. Ordinary quoted sends, search/open-result and channel-thread read/history entry points are restored. Chat unread uses the selected-message replacement; channel writes and the old chat-level unread entry point remain unsupported.

## Disabled capabilities and proposed extensions

These remain distinct from missing web parity:

| Work | Status / enabling condition |
| --- | --- |
| Explicit channel read/unread | Both gates are false. Verify native marker scope in a designated channel and prove that unrelated unread sibling threads remain protected. The web plugin had read side effects when opening channels, not a dedicated selected-message channel read-state contract. |
| Automatic read-after-reply | `readAfterReply=false`. The durable read stage is fixture-tested, but needs independent verification of bookmark handling and unread-generation protection before enabling it. This is a new explicit workflow, not a removed standalone web operation. |
| Channel replies | This **is** missing web parity. Keep the candidate disabled until exact-root native request and live-send verification passes. |

Attachments/file upload, group-chat creation, arbitrary full emoji-picker search, and legacy Posts-layout channel writes were not supported by the retained web plugin. They may be future extensions, but should not be counted as API-migration regressions. Both adapters bound reads and exclude unavailable/retained/deleted history; neither guarantees a full account archive.

## Remaining validation from earlier roadmap entries

- **Live message writes:** validate plain/formatted chat sends, quoted replies, edits, deletion and reactions in designated conversations. No live message was sent during the read-state work. Fixture success and enabled source-verified chat quotes are not evidence of a live send.
- **Channels:** validate actual root/reply coverage and deep per-thread traversal before claiming full thread parity; native channel sends and marker scope have not been designated or live-verified.
- **Central Switchboard:** On 2026-10-08, laptop auth:sync successfully triggered server HTTP renewal on the existing central imported-token connection and verified readiness without a browser or upload. Reconnect upload, account binding after reconnect and central durable ledger recovery remain to be checked.
- **Authentication expiry and recovery:** test rotation across the SPA refresh-token expiry boundary, terminal revocation/MFA recovery and tenant-specific sign-in policy. HTTP renewal has passed locally; token lifetime and headless cookie-only reacquisition remain unverified.
- **Diagnostic session reuse:** the shared owner-only cache and refresh-rotation persistence have restart/account/concurrency fixture coverage. On 2026-10-08, one initial session capture, a separate silent API check, forced browser-closed HTTP renewal, and subsequent feature checks all reused the shared saved session successfully. Reuse a saved session for live checks; request fresh browser capture only when testing capture or when renewal cannot recover it.
- **Scale and concurrency:** validate partial discovery, large-account pagination, older roots/replies and external changes during writes. Existing-message suffix preservation passed live; newly injected arrivals and races have fixture coverage. Private endpoints offer no atomic compare-and-set.
- **Independent review:** review private API contracts, uncertainty handling and migration compatibility before relying on broader write support.

## Completed evidence and changes

- **0.11.0:** server message/people search, exact search-result opening, virtual one-to-one resolution, structured person mentions, direct exact-ID chat quotes, channel-root listing and per-thread read/history routes are implemented on `feat/teams-api-parity`. Browser-closed live checks passed optional search-token renewal, name suggestions, message search, opening a chat hit, exact message reads, channel roots/continuation, exact thread reads and NDJSON thread export. No messages were sent. New-chat persistence, mention notifications and quoted sends still need designated-recipient live checks; channel writes remain disabled. The full suite passed 150 tests. See [parity protocol evidence](docs/parity-protocol.md).
- **Small follow-up to 0.10.0:** shared cleared-bookmark boundary handling now also fixes the flat unread helper. Saved diagnostic session reuse and forced HTTP renewal passed across separate commands. Central auth:sync reported server_renewed with fresh expiry and no browser/token upload.

- **0.10.0:** selected-message chat read/unread batches, native horizon/bookmark captures and browser-closed regular-chat readback passed on 2026-10-08. Checks covered inclusive boundaries, preserving an existing later unread message, replay without restoring old unread intent, and restoration to the test chat's original read state. The ordinary horizon was never rewound. Channel gates and automatic read-after-reply remain disabled. Shared diagnostic session persistence and HTTP refresh reuse are implemented. The full suite passed 137 tests. See [protocol evidence and limits](docs/triage-protocol.md).
- **0.9.0:** grouped paginated triage, batched context refresh and source-verified native quoted chat replies are implemented. Browser-closed inbox/context reads passed locally; channel completeness and live quoted sends remain separate validation work.
- **0.8.1:** laptop `auth:sync` implements readiness/expiry checks, a server renewal probe, in-memory token reconnect upload and status verification; server renewal subsequently passed; reconnect-upload and durable-ledger validation remain outstanding.
- **0.8.0:** browser refresh-token capture, browser-closed HTTP renewal of both Microsoft access tokens, chat-token exchange/account binding, profile and conversation reads passed locally. Production on-demand renewal, rotated-token storage and portable version 2 bundles have fixture coverage. Imported connections do not launch a browser on the host.

Earlier statements that chat read markers were entirely unverified or that the Node adapter still needed its first local read-only check are superseded by this evidence. Completed checks do not close reconnect-upload, broader-write or expiry-policy items above.
